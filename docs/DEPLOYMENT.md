# Deploy Nova publicly

Recommended: Vercel frontend + Render Python API. The frontend is publicly viewable; assistant usage requires the owner's workspace access code. The provided Render Starter service and persistent disk incur hosting charges. Review the current dashboard price before creating the service.

## 1. GitHub

Push this project to the root of `charandeepreddy329-ctrl/Ai-Voice-Assistant-v2`. Use `main` for the initial deploy. CI runs the backend tests and Vite production build. If using another branch, choose the same branch in both hosting dashboards.

## 2. Create the Vercel project

Import the GitHub repository, select Vite, and set Root Directory to `frontend`. Build command `npm run build`; Output Directory `dist`; install `npm ci`. Deploy the initial UI and record its exact production HTTPS origin. The UI can render before the backend is connected.

## 3. Create the Render API

In Render choose New → Blueprint → this repository. Render reads root `render.yaml`, builds `backend/Dockerfile`, and mounts a persistent disk at `/data`. Confirm the paid service/disk selection in your own account.

Set these environment variables:

| Variable | Value / handling |
|---|---|
| `SESSION_SECRET` | Generated by Render blueprint. Keep stable across deploys; rotation invalidates sessions. |
| `ACCESS_CODE` | Private random code, at least 12 characters. Share only with intended visitors. |
| `ALLOWED_ORIGINS` | Exact Vercel production origin, e.g. `https://your-project.vercel.app`; no trailing slash or wildcard. Comma-separated for additional approved origins. |
| `LLM_PROVIDER` | `compatible` for hosted inference |
| `LLM_BASE_URL` | Provider's HTTPS API prefix ending in `/v1` if required; adapter appends `/chat/completions` |
| `LLM_API_KEY` | Provider key; backend only |
| `CHAT_MODEL` | A model ID supported by your provider's chat-completions endpoint and `max_tokens` parameter |
| `REASONING_MODEL` | Compatible reasoning/code model ID; may equal CHAT_MODEL |
| `DATABASE_PATH` | `/data/nova.db` (already set) |
| `GLOBAL_REQUESTS_PER_MINUTE` | `60` default; lower for cost control |

The adapter is provider-neutral; model names cannot be finalized until a provider is selected. Use an endpoint that supports non-streaming `messages` and `max_tokens`. Do not assume every reasoning model supports that payload.

Do not put API credentials in GitHub source, frontend environment variables, screenshots, or URLs. Hosting account login and model keys must be supplied through provider settings, not committed files.

## 4. Connect the frontend

Copy the Render HTTPS service URL. In Vercel set `VITE_API_URL` to that origin (without trailing slash) for Production. Redeploy the frontend because Vite embeds this value at build time. Check ALLOWED_ORIGINS matches the actual frontend production domain. Explicitly add custom domains; preview domains are blocked unless separately allowed.

## 5. Verify the live deployment

- Open API `/healthz`: expect `{"status":"ok"}`. This checks the API, not model readiness.
- Open frontend over HTTPS and connect with access code.
- Send a calculation; save and read a note; test a real AI question.
- In a separate browser session, verify the first session's notes are not visible.
- Permit microphone access; record, stop, review transcript and send. Enable voice replies.
- Generate/download Python; check content without executing it.
- Delete your test data in the workspace privacy panel.
- Restart the backend and confirm retained notes survive on the disk.

## Operations

Keep one API instance and one worker: SQLite disk and in-process throttling assume this layout. Set provider billing caps, monitor errors/storage, and configure disk backups in the hosting account. No automatic backups or expired-session cleanup are configured. This is a limited-access personal assistant deployment, not an anonymous high-traffic SaaS.

If you want unrestricted public AI usage, first add proper identity/abuse controls and spending limits; do not merely publish ACCESS_CODE in the frontend. See architecture notes for scaling requirements.
